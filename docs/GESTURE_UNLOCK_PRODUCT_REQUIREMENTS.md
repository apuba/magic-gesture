# 魔法手势：手势权重与每日签到解锁需求

> 文档状态：产品规则已确认；**代码已于 2026-10-02 实现**（离线签到解锁链路完成并通过 JVM 测试与 Debug/Release 构建），尚未真机验收
> 创建日期：2026-10-02  
> 代码基线：`GestureUnlock.kt`（解锁计划、状态机、本机存储、开关收敛）、`GesturePreferences.effectiveFeatures()`、`CameraProbeService` 权益门控、`MainActivity` 签到卡片、`CalibrationActivity` 锁定态
> 适用范围：现有 G01–G35，不新增 G36 及后续手势
> 重要边界：当前正式版需要实现离线每日签到解锁，但不设置任何收费用户或付费入口；账号、微信登录、付费、邀请、分享奖励、服务端和联网权益仍属于二期记录，真实上线前不得开发。

## 1. 背景与目标

当前应用已经具备 G01–G35 共 35 个真实识别编号。一次向新用户展示全部手势，会增加理解和学习成本，也不利于判断哪些功能真正有价值。

本需求希望探索以下产品机制：

1. 按预期使用频率和用户价值重新排列手势，而不是按 G 编号展示。
2. 新用户初始只开放一组足以完成基本操作、同时能体现产品特色的手势。
3. 用户通过每日主动签到，逐步解锁新的手势功能包。
4. 当前正式版所有生产用户适用同一规则，不存在付费用户或付费全开。
5. 账号、付费全开和邀请真实新用户奖励只作为二期想法记录。

当前没有真实线上用户行为数据，因此本文权重属于**产品假设**，不能宣称为真实使用率排名。App 上线后必须依据实际数据、用户访谈和售后反馈重新校准。

## 2. 不可突破的产品边界

- G35 已由产品负责人确认纳入当前正式范围；不再新增 G36 及后续新手势，现阶段只测试和优化 G01–G35。
- 当前正式上架版本必须包含离线每日签到解锁；代码已实现，尚未完成真机验收，不能把代码完成或构建通过写成真机通过。
- 当前版本不设置收费用户、会员、订阅、付费解锁入口或隐藏付费状态。
- 安全入口和基础设置永远不能被锁定，包括停止控制、权限管理、校准、冷却设置、隐私说明和故障恢复。
- 锁定手势不得继续在后台识别或执行；不能只隐藏首页卡片。
- 功能开关、动作映射和解锁权益是三种不同状态，不得混为一层：
  - 解锁权益：用户是否拥有该手势。
  - 功能开关：拥有后是否启用识别。
  - 动作映射：识别成功后执行什么动作。
- 失败不得伪装为签到成功、解锁成功或动作成功。
- 所有正式 Release 用户执行同一套签到解锁规则，不设置历史用户自动全开、管理员全开或秘密解锁口令。
- Debug/内部测试构建必须能全部解锁，以完成发布验收；该测试能力不得进入正式 Release。

## 3. 权重计算建议

初始排序采用以下四项产品评分：

| 维度 | 权重 | 说明 |
|---|---:|---|
| 日常使用频率 | 35% | 用户在多数 App 中使用该动作的预期频率 |
| 通用价值 | 30% | 是否跨 App、跨场景可用 |
| 识别成熟度 | 20% | 当前真机稳定性、误触风险和机型兼容性 |
| 学习成本 | 15% | 姿势是否直观、是否容易记忆和完成 |

上线后应使用真实数据替换主观权重，至少关注：首次成功率、日/周触发次数、误触率、关闭率、换绑率、签到后实际使用率和功能相关卸载反馈。

## 5. 初始开放手势

所有正式用户初始开放 7 个编号：

- G01 光标
- G02 点击
- G03/G04 上下滚动
- G24 返回
- G11 自拍
- G13 截图

这一组合同时满足：

- 能移动、点击、滚动和返回，形成基本控制闭环。
- 免费体验包含自拍和截图两个有辨识度的功能。
- 不会在用户尚未感受到价值之前就要求签到。

`N=7` 已确认为当前正式版需求：所有正式用户首次获得以上 7 个编号，其余功能包通过每日签到依次解锁。

## 6. 当前正式版：离线每日签到解锁

> 状态：产品规则已确认，代码已实现（2026-10-02）。实现未引入账号、支付、分享、联网或服务端依赖。
> 三层落地方式：解锁权益在 `GestureUnlock.kt`；功能开关仍是 `GestureFeatureConfig`；动作映射仍是 `GestureMappingManager`。未解锁手势在识别入口（`GesturePreferences.effectiveFeatures()`）和执行入口（`CameraProbeService.executeMapped`、持续音量会话）双重拦截。

### 6.1 建议解锁顺序

以“功能包”为单位，不拆散共用开关或同一动作族：

| 累计签到 | 解锁功能包 |
|---:|---|
| 第 1 天 | G22 播放/暂停 |
| 第 2 天 | G31/G32 持续音量控制 |
| 第 3 天 | G29/G30/G33 上一曲、下一曲与双击播放暂停 |
| 第 4 天 | G23 静音开关 |
| 第 5 天 | G21 收藏当前内容 |
| 第 6 天 | G16/G17 打开常用 App |
| 第 7 天 | G18/G19 更多 App 快捷入口 |
| 第 8 天 | G14/G15 桌面与最近任务 |
| 第 9 天 | G05/G06 四指上下滚动 |
| 第 10 天 | G07–G10 横向滚动包 |
| 第 11 天 | G25/G27/G28 通知栏与系统导航替代姿势 |
| 第 12 天 | G12/G20 点赞手势 + G26/G34/G35 高级手势 |

第 12 次签到后 G01–G35 必须全部拥有。G26、G34 仍保持默认未绑定，但解锁完成页必须明确引导用户进入动作映射选择用途，不能只显示“未绑定”后结束；G35 保持默认绑定“向上滑动”。

### 6.2 签到规则

- 用户必须主动点击“今日签到”，打开 App 本身不自动领取。
- 每个自然日最多领取一次。
- 断签不清零，不使用连续签到惩罚。
- 已解锁权益永久保留，不因漏签而收回。
- 首页提前展示“下一次将解锁什么”。
- 锁定手势允许查看姿势、用途和解锁条件，但禁止执行、换绑和开启识别。
- 本地阶段允许存在修改系统日期、清除数据、卸载或换机导致的限制，不为 MVP 建造复杂反作弊系统。
- 如果一期没有账号，必须明确提示解锁记录只保存在本机，卸载或清除数据可能丢失。

### 6.3 正式用户与测试构建

- 所有正式 Release 用户统一从 7 个基础编号开始，通过每日签到解锁后续功能包。
- 不设置历史用户自动全开、收费用户全开、管理员全开或正式包隐藏口令。
- Debug/内部测试构建允许全部解锁，用于覆盖 G01–G35 验收；测试能力必须通过明确的构建类型隔离，不能依赖普通用户可触发的隐藏点击。（已通过 `BuildConfig.DEBUG` 实现并验证）
- 不得仅依据当前功能开关判断拥有权益；关闭功能不等于未解锁。
- 正式版本升级和数据迁移必须可重复执行，不能丢失用户已经通过签到获得的权益。
- 一共 12 次有效签到后 G01–G35 全部拥有，签到解锁流程结束，不继续制造无意义积分或签到任务。

## 7. 二期候选能力：真实上线后重新规划

> **硬门槛：二期只有在 App 已经真实公开上线后才能重新立项。** 真实上线前，本节所有内容只作想法记录，不是开发需求、排期或验收依据。

二期候选范围包括：

- 微信登录或其他账号体系。
- 游客身份升级为正式账号。
- 服务端同步解锁权益。
- 付费用户一次性解锁全部稳定手势。
- 恢复购买、退款、换机和多设备权益同步。
- 邀请码、邀请链接和分享给新用户获得解锁券。
- 防刷、设备识别、异常注册和奖励上限。
- 线上行为统计与解锁顺序调整。

### 7.1 二期启动条件

以下条件缺一不可：

1. App 已在至少一个目标应用市场完成真实公开上架，而非仅生成 Release 包或进入内部测试。
2. 已积累首批真实用户反馈或使用数据。
3. 产品负责人重新确认商业模式、市场范围、支付渠道和隐私边界。
4. 重新编写二期 PRD、接口契约、账号状态机、支付状态机和验收标准。
5. 明确服务端、数据库、部署、运维和安全责任。

任何 AI 或开发者不得直接依据本文件实现微信登录、支付、邀请分享、服务端或联网统计。

### 7.2 付费解锁原则记录

- 付费用户直接解锁全部已经稳定验收的手势，不继续受签到进度限制。
- 支付成功必须由可信支付结果或服务端查询确认，不能仅凭客户端成功回调。
- 必须支持恢复购买、退款处理、换机和账号权益同步。
- 必须提前定义“永久解锁”是否包含未来新增能力，避免宣传和售后争议。
- 未通过真机验收的手势不能作为付费价值承诺。

### 7.3 邀请新用户原则记录

- 不能以“打开分享面板”或“点击分享”作为奖励条件。
- 合格邀请至少需要服务端确认新用户首次安装、启动并完成有效激活。
- 需要邀请码或可归因链接、每日奖励上限、同设备/同账号防刷和异常处理。
- 分享文案不能诱导骚扰联系人。
- 微信登录不应成为使用基础免费功能的强制条件。

## 8. 解锁机制利弊

### 8.1 预期收益

- 降低 35 个手势一次性展示带来的学习压力。
- 每天学习一个功能包，更容易形成使用习惯。
- 为次日、七日留存提供明确目标。
- 帮助用户逐步发现低频但有价值的功能。
- 为用户提供渐进式教学和明确的每日学习目标。

### 8.2 主要风险

- 用户可能认为应用人为锁住已经完成的能力。
- 初始免费能力不足会导致用户在体验价值前卸载。
- 固定顺序可能连续解锁用户不需要的功能。
- 手势识别不稳定时，签到奖励会被理解为“奖励了一个坏功能”。
- 解锁权益、功能开关和动作映射叠加后，状态与测试复杂度明显增加。
- 离线签到可被修改日期绕过，并可能因卸载或清除数据丢失。
- 登录、支付和分享会引入隐私、合规、退款、防刷和服务端运维成本。

进入代码实施前必须补充的内容，以及当前实现状态（2026-10-02）：

| 验收项 | 状态 |
|---|---|
| 锁定、可领取、已解锁、已启用、已关闭、已换绑的完整状态定义 | 已实现：基础编号 + 12 个功能包决定“拥有”；`feature_*` 决定“已启用”；`mapping_Gxx` 决定“已换绑”；签到状态机给出“可领取 / 当日已领取 / 已完成” |

| 签到跨天、时区变化、系统时间回拨和重复领取处理 | 已实现：按本地时区 epochDay 判定；同一天重复领取被拒绝；时间回拨视为当日已领取，不清零已解锁权益 |
| 老用户升级与解锁数据迁移测试 | 已实现代码路径（缺失偏好即为 0 次签到，仅拥有 7 个基础编号），**尚未在真机做升级验证** |
| 清除数据、卸载重装和换机提示 | 已实现：首页签到卡片固定显示“解锁记录只保存在本机，卸载或清除数据可能丢失” |
| 无障碍服务运行中解锁后是否即时生效 | 已实现：签到写入 `unlock_*` 偏好后，控制服务的偏好监听立即刷新权益并下发到识别引擎 |
| Debug 全开与正式 Release 签到解锁的构建隔离验证 | 已实现并验证：`BuildConfig.DEBUG` 控制全开；`assembleRelease` 生成 `BuildConfig.DEBUG=false`，`assembleDebug` 为 `true` |

尚未完成：真机签到流程验收、升级迁移验证、G26/G34 解锁完成后的引导验收，以及 G35 解锁后短视频翻页和互斥稳定性验收。

## 10. 当前结论

当前产品规则已经确认且代码已实现，但尚未完成真机验收。正式上架前的工作顺序为：

1. G01–G35 真机测试与阈值稳定。
2. 高质量自拍、G23 1 秒等现有功能验收。
3. 真机验证 7 个基础编号加 12 次离线签到解锁机制。（代码已实现）
4. 隐私、权限、应用市场材料和正式 Release 准备。
5. App 真实上线。

真实上线之后，再根据实际用户数据重新规划账号、支付、付费全开和分享邀请；不得直接沿用当前二期想法开工。
