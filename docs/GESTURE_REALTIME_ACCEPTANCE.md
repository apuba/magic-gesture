## 三、本轮修复

### 3.1 G12 指尖比心识别阈值（`GestureEngine.kt`）

**现象**：真机保持比心 3 秒，一次未触发，连候选状态都没进入。

**实测数据**（临时诊断，用完已移除）：

```
tip=0.36~0.40  pip=0.36~0.44  mcp=0.93~1.07  i85=1.20~1.35
食指 idxOpen=true（伸直）  中/无名/小指 全部收拢
gun=false  fist=false  tfe=false  okOwn=false  thumbUp=false
```

**根因**：`thumbMeetsIndexTip` 阈值 `0.40` 恰好压在实测值 `0.36~0.40` 的上界，手稍微旋转就越界，姿势直接落空。

**改动**：

| 项 | 原值 | 新值 | 说明 |
|---|---|---|---|
| `thumbMeetsIndexTip` | 0.40 | **0.46** | 留出余量 |
| `thumbPressesIndexJoint`（PIP） | 0.32 | **0.40** | 兼容压关节握法 |
| 新增 `thumbMeetsIndexTipStrict` / `thumbPressesIndexJointStrict` | — | 沿用原值 | **G24 枪专用**，避免放宽后心形手反过来否决"返回" |

同时按实测修正注释：真实比心的食指是**伸直**的（原注释写"明显弯曲"，与实测相反）。

**验证**：110 个单元测试通过；真机连续 3 次比心均触发。

### 3.2 此前的保持类重复触发修复（已完成）

G22 / G23 触发后保持不动、冷却结束即重复执行的问题，已通过"触发锁存跨冷却保留 + `lost()` 需连续消失 600ms + `RELEASE_GRACE_MS=800`"修复，复验通过。

### 3.3 拇指松紧判据：`thumbWideOpen`（G16–G19 / G23）

**现象**：G18「张掌变三指」进了 HOLDING、三指已被识别，却在 600ms 保持完成前被取消；G23 小指手势被判成 G34 六六顺。

**实测数据**：

```
02:58:11.279  seq=HOLDING  s8=t s12=t s16=t s20=f  thumbOpen=false  ← 三指成立
02:58:11.591  seq=HOLDING  ...                     thumbOpen=true   ← 拇指判定翻成"张开"
02:58:11.772  seq=WAIT_RELEASE                                       ← 未满 600ms 即取消
```

**根因**：`thumbOpen = dist(4,5) > dist(3,5) * 1.05` 过于敏感；伸出三指/四指或小指时拇指会自然微张，判定在 true/false 之间抖动。

**改动**：新增 `thumbWideOpen = dist(4,5) > dist(3,5) * 1.25`，G16–G19 的四个槽位与 G23 统一改用 `!thumbWideOpen` —— 只有**明显张开**的拇指才否决。G34 仍用宽松的 `thumbOpen`，两者通过判定优先级互斥（1.05–1.25 的模糊区间归 G23）。

**验证**：G16 / G17 / G18 / G19 复验通过；G23 复验通过且不再误判为 G34。

### 3.4 G26 抓取（爪形）改为默认关闭

**现象**：一轮操作里 G26 触发 16 次，而单指上下游滚动与左右挑几乎抢不到帧；G05/G06 并掌挥动时也被判成拖动。

**根因**：爪形读数覆盖"任意半弯的手"，且它在流水线中位置靠前。产品上 G26 本就处于"未绑定动作"状态，没有真实使用场景。

**改动**：`GestureFeatureConfig.clawDrag` 默认 `false`，抽出常量 `CLAW_DRAG_DEFAULT`，用户可在校准页开启。

**踩坑记录**：第一次只改了 `data class` 的默认值，结果**完全没生效** —— `features()` 里是硬编码的 `prefs.getBoolean("feature_claw_drag", true)`，把 data class 的默认值绕过了。必须让两处引用同一个常量，否则默认值形同虚设。

### 3.5 G33 双指双点：时间窗放宽与抢占抑制

**现象**：用户认为做完了标准双击，日志零触发。

**实测数据**（临时诊断，用完已移除）：

```
成功 11:53:56  pose保持1634ms → 弯108ms → 伸467ms → 弯103ms → FIRED
失败 11:54:20  第一次弯后隔 1555ms 才第二次弯 → 超 1200ms 窗口 → 回 IDLE
失败 11:54:02  弯后 2277ms 才回来        → 超 500ms 回位窗 → 回 IDLE
```

**改动**：

| 项 | 原值 | 新值 | 依据 |
|---|---|---|---|
| 回位窗（`twoFingerTapReturnMs`） | 500ms | **900ms** | 实测用户两下之间常隔 1.5 秒以上 |
| 两次弯下的总窗口（`twoFingerTapCycleMs`） | 1200ms | **2200ms** | 同上，旧窗口把一次完整双击切成两次失败 |
| 比心（G12）抑制 | 无 | 双击进行中清零 `pinch` | 双指弯下会让指尖贴上拇指，正是比心的读数 |
| 音量/切歌抑制 | 只覆盖双击后半程 | 补上 `BENT_ONCE` | 第一下弯后的位移会被判成上下拉音量 |

**验证**：连续 3 次双击全部触发，且过程中 `G12 LIKE` 一次未出现。112 用例通过。

> 注：此前"必须慢一点、弯到位"的提示是**错的方向**，真实双击的特点是"每一下弯得很短（~100ms），两下之间隔得久"，现已按实测纠正。

### 3.6 G09/G10 默认关闭 + G03/G04 加瞬时角速度门槛

**背景**：负责人反馈「G01 光标容易与 G09/G10 冲突」。

**实测数据**（A 组真挑 vs B 组慢速移光标，诊断代码已移除）：

```
            真挑触发时的累计位移      慢速移光标的累计位移
G09/G10     dx = 0.054 / 0.084 / -0.053   dx = -0.062 → -0.255
```

关键点：G09/G10 的判据只有位移门限 `.05 * movementScale`，**没有任何速度项**。慢慢移动光标时累计位移达到真实挥动的三到五倍，之所以多数时候没误触，只因那一帧的 `horiz`（水平占优）或 `wHand`（手腕跟随）碰巧不成立 —— 属于运气，不是机制保证。

**改动一（G09/G10）**：抽出常量 `INDEX_HORIZONTAL_SCROLL_DEFAULT = false`，左右滚动交给形态完全不同的 G07/G08 并掌挥（已全部验证通过）。新增用例 `verticalIndexStaysSilentWhileIndexWavesAreOff` 守住这个默认值。

**改动二（G03/G04）**：保留但加角速度门槛。这里有个陷阱 —— **不能用总耗时做门槛**：

```
真挑 G03/G04 都在 el = 1.0~1.4s 才完成（识别到水平食指后用户会先停一下再挑）
慢速移光标 0.7~1.3s 内角度漂移 < 4°
真挑最后一帧（100~180ms 内）角度突变 22.9° / 27.9° / 29.4° / 31.3° / 40.9°
```

两者真正的差别在最后一瞬的**角速度**，相差六到十倍。因此取最近 150ms 窗口内的角度变化量作为门槛，要求 ≥ 18°（`indexFlickSlewWindowMs` / `indexFlickSlewDeg`），与方向同符号。慢速漂移永远跨不过，真挑保留约 20% 余量。新增用例 `slowlyDriftingIndexAngleNeverScrolls` 防止回归。

**验证**（114 用例通过）：G03 ×2 / G04 ×2 正常触发；慢速上下移光标 3 次、慢速左右移光标 3 次，**零滚动**；G09/G10 全程静默。

### 问题 6：过渡姿势误识别（2026-10-04 已处理，待真机复验）

- **现象**：在"抬手准备 / 换姿势 / 放手"的空档被判成别的手势。
- **观测样本**：`10:10:07 G19`、`10:10:59 G18`（张开掌准备抓取时）、`12:11:52 G22`、`12:43:30 / 35 / 44 / 12:50:17 G12`（手指靠拢瞬间被判比心）、早期 `G07`、`G27` 若干次；最近一轮另有 `11:45:04 G27`、`11:49:52 G07`、`11:54:07 G12`。
- **性质**：与按键消抖同类 —— 换姿势途中的手形是无效输入，需要一个"进入明确姿势后才允许出事件"的闸门。
- **影响**：多数目标是切换应用/最近任务/播放暂停，属可接受但不理想。
- **处理（`GestureEngine.kt`）**：新增过渡闸门 `updateShapeStability`。每帧记录拇指尖与四个指尖**相对手腕、按掌宽归一化**的坐标，算出集体的形变速度（掌宽/秒）；超过 `shapeChangeSpeed`（3.0）判定为"还在摆姿势"，此后必须静止满 `shapeSettleMs`（60ms）才恢复 `shapeSteady`。静态保持类（G12 比心、G14/G15、G20–G23、G24/G25、G27/G28、G34/G35）与 G16–G19 的槽位保持都要 `shapeSteady` 才开始计时，计时途中一旦又变形就把计时推回当前帧；G12 在候选期间遇到变形同样重新计时。轨迹类（挥/滚/拖动/音量/张掌序列）不受影响 —— 相对手腕的坐标对整体平移免疫，手在画面里移动不算变形。
- **代价**：换姿势后每个静态手势要多等约一帧到几十毫秒才开始计时，用户感知不到；回放用例中受影响的"重入"段已相应加帧，`lotusAndOrchidHoldFireTheirOwnActionWithoutCrossTriggering` 改为在两个姿势之间放下手，符合真实操作。新增用例：`aHandThatKeepsReshapingNeverFiresThePoseItPassesThrough`、`carryingAPoseAcrossTheFrameStillFiresIt`。
- **状态**：✅ 代码实现与 JVM 测试通过（116/116），**待真机复验**：既要看老样本的 G12/G27/G07 是否消失，也要用 `diag: shape speed=...` 看真实形变速度分布，据此复核 3.0 这个阈值（偏大会漏拦，偏小会让正常手势变迟钝）。

## 五、验收方法备忘

每批手势开一个独立日志文件，操作完成后统计：

```powershell
$adb = "D:\Android\Sdk\platform-tools\adb.exe"
& $adb shell "pkill -f 'logcat -f'"
& $adb shell rm -f /sdcard/mg_batch.log
& $adb shell logcat -c
& $adb shell "nohup logcat -f /sdcard/mg_batch.log -v time >/dev/null 2>&1 &"
# ... 用户做手势 ...
& $adb shell "grep -a -E 'gesture G(0[2-9]|[1-9][0-9]) ->' /sdcard/mg_batch.log"
```

启动服务：`adb shell monkey -p com.magicgesture.app -c android.intent.category.LAUNCHER 1`，再点击开始按钮。**按钮坐标不能用固定值**：主页面是可滚动列表，滚动位置不同则坐标不同，本轮先后出现过 `600 1204`、`600 1656`。可靠做法是先 dump 再取中心点：

```powershell
& $adb shell uiautomator dump /sdcard/ui.xml
$ui = & $adb shell cat /sdcard/ui.xml
foreach ($n in [regex]::Matches($ui,'<node[^>]*clickable="true"[^>]*>')) {
    $t = [regex]::Match($n.Value,'text="([^"]*)"').Groups[1].Value
    if ($t -match "启动手势控制") {
        $b = [regex]::Match($n.Value,'bounds="\[(\d+),(\d+)\]\[(\d+),(\d+)\]"')
        if ($b.Success -and (([int]$b.Groups[4].Value - [int]$b.Groups[2].Value) -gt 80)) {   # 过滤渲染未完成的 1px 节点
            & $adb shell input tap ([int](([int]$b.Groups[1].Value+[int]$b.Groups[3].Value)/2)) ([int](([int]$b.Groups[2].Value+[int]$b.Groups[4].Value)/2))
        }
    }
}
& $adb shell dumpsys activity services com.magicgesture.app   # 出现 ServiceRecord 才算起来
```

判据无法从日志反推时，临时在 `GestureEngine.kt` 加 `diag` 输出关键几何量（120–200ms 限流），定位后立即移除。本轮用此法定位了 G12、G24、G33、G09/G10 与 G03/G04，诊断代码均已清理，`git diff` 中不应残留 `diag`。

**加诊断的三条经验**（本轮都踩过）：

1. **每个探针用独立的限流时钟**。两个探针共用 `lastDiagAt` 时，先执行的那个（每帧都成立）会把额度占光，另一个一行都打不出来。
2. **务必看矩阵**：要看的是"成功 vs 失败"两组数据的**分布差别**（如 G03/G04 的角速度），而不是成功那一组能不能跑通。只看成功样本会得出错误结论。
3. **先确认目标手势会不会写日志**。G31/G32 走系统音量接口、G26/G34 默认未绑定，这四类**都不产生 `gesture Gxx ->` 行**。曾据此把正常工作的 G31/G32 误判为"零触发"。
