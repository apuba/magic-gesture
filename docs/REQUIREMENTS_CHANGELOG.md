# MagicGesture 需求变更记录

> 本文档持续记录产品负责人已经明确确认、会影响现有功能行为的需求变更。  
> 这里只记录 G01–G35 现有范围内的稳定性、交互和发布需求，不作为新增手势或二期功能的开发授权。

## 2026-10-07：Love 手势（G28）改为系统级识别锁

- 产品负责人确认：把“锁定／解锁整条手势识别”的锁定动作绑定到 **Love 手势（G28）**，不再使用六六顺（G34）。G34 保持原样，仍是第 12 次签到解锁、默认未绑定的普通手势。
- G28 不再是普通动作手势：原默认动作“返回桌面”取消，G28 不进入动作映射、不参与功能开关、不可换绑；用户此前保存的 G28 映射也不会让它执行任何动作。
- 状态机：Love 姿势稳定保持 1 秒切换锁定状态；锁定期间只有 Love 姿势被识别，G01–G35 其余姿势、光标、反馈、保持进度、轨迹、序列、双击与持续动作一律不识别、不累计、不输出；切换后姿势须连续消失 800ms 才能再次切换，持续保持不能反向切换。
- 识别锁是控制状态而非动作：不进入 `GestureMappingManager`／`GestureActionExecutor`，也不因切换锁状态启动全局动作冷却；普通动作冷却期间整条管线冻结，不会提前判断 Love 姿势。
- 锁定前若正在拖动或持续音量，先安全发送结束事件再清空状态；解锁后等姿势完整释放再恢复识别，不补发半个动作。
- 锁定不停止服务：摄像头、MediaPipe 手部检测与视觉最近手选择继续运行，因此不释放摄像头、不降低耗电；继续遵守最近手独占控制权。
- 手动解除入口：首页“🔓 解除识别锁定”按钮（仅锁定期间显示）与常驻通知“解除锁定”动作，统一走 `CameraProbeService.ACTION_UNLOCK_RECOGNITION`。
- 签到权益调整：G28 从第 10 天功能包（`G25/G27/G28`）移出，改为所有用户一开始就拥有的系统级控制；基础动作编号仍为 7 个，识别锁不计入其中，也不随签到解锁。
- 代码已完成并通过 JVM 测试与 `assembleDebug`；**尚未真机验收**。真机验收清单见 `GESTURE_UNLOCK_PRODUCT_REQUIREMENTS.md` §6.5.4。
- 同步更新：`docs/GESTURE_ACTION_MAPPING_CHECKLIST.md`（G28 行与阅读约定、待校准项）。

## 2026-10-06：签到后不得重新显示已完成的首次使用设置

- 现象：悬浮窗与无障碍授权均已完成且“首次使用设置”正常隐藏时，点击签到后两个授权选项会重新显示。
- 根因：签到成功会原地重建首页，以立即更新解锁卡片与开关；新建的设置容器默认可见，而重建函数遗漏了授权状态刷新。
- 修复：每次首页原地重建后立即重新读取悬浮窗与无障碍授权状态；两项均已完成时继续隐藏设置区域，缺少任一项时仍正常显示引导。
- 本项不改变签到状态机、解锁顺序、系统权限或控制服务。

## 2026-10-06：G35 增加拇指侧伸角度与关节距离约束

- 真机反馈：普通竖起并拢双指容易被判定为 G35“双指枪·竖向”，说明原有拇指侧伸条件不足以排除自然贴在掌侧的拇指。
- G35 继续要求食指与中指并拢向上、无名指与小指收拢并稳定保持 1 秒；拇指必须明显向侧面伸出。
- 参考 G24，拇指方向与食指方向夹角限定为 45°–90°，同时拇指尖须远离食指 MCP/PIP，夹角过小、超过 90°或自然贴掌均不得进入 G35 保持。
- 进一步增加左右手方向约束：MediaPipe 判定为右手时拇指必须向画面右侧伸出，判定为左手时必须向画面左侧伸出；方向相反或手别缺失时不进入 G35。校准页开启“反转左右方向”后同步转换手别标签，保证坐标与手别关系一致。
- 本次只收紧 G35 几何条件，不改变编号、保持时长、功能开关、签到包、动作映射或 G29–G33 双指媒体手势。
- 新增普通贴掌双指、大于 90°拇指方向、左右手方向相反及手别缺失不得触发 G35 的回放覆盖。
- **2026-10-06 真机验收通过**：最新 Debug 包中，右手拇指向右、左手拇指向左可正常识别；反向和普通竖起双指不再误触 G35。

## 2026-10-04：G11 自拍固定适配当前屏幕比例

- G11 不提供照片比例选项，所有用户统一使用当前屏幕比例。
- 自拍仍优先使用前置摄像头可与 640×480 识别流稳定并发的最高 JPEG 分辨率；最大尺寸组合失败时按像素面积从高到低尝试其他 JPEG 尺寸，全部失败后才回退识别预览帧。
- 照片完成方向校正后按拍摄开始时的物理屏幕宽高比居中裁剪，不拉伸，不缩小到屏幕分辨率；裁剪后保留该比例下能够得到的最大像素尺寸。
- 全屏裁剪或高分辨率解码失败时优先保存方向正确的原始高清照片，不因裁剪失败丢失一次有效自拍。
- 日常识别继续使用 640×480；全屏裁剪只发生在自拍保存线程，不改变 G11 保持 2 秒、倒计时 3 秒及倒计时期间冻结全部识别的规则。
- **2026-10-04 真机验收通过**（Honor，当天最新 Debug 包，证据见 `GESTURE_REALTIME_ACCEPTANCE.md` 6.5）：实际输出 `1476×3264`（704KB），由传感器最大 JPEG `3264×2448` 转正后按物理屏幕比例居中裁边得到，保留了 3264 这条最大长边；方向、前置镜像、倒计时静默、拍完识别恢复、2 秒手感均由操作者确认正常。仍缺保存耗时、内存峰值、连续连拍与「高质量失败回退预览帧」的真机触发。

## 2026-10-04：OK（G21）不再被「张开掌」类流水线和打开应用序列抢走

- **现象**：做 OK 手势时执行了「打开应用」，或不执行任何动作（`gesture G21 -> FAVORITE_CURRENT` 不出现）。2026-10-04 由操作者真机发现。
- **根因**：OK 的判据是「拇指尖与食指尖相触 + 中指/无名指/小指伸展」。逐指数下去它就是**一根拇指 + 四根伸出的手指**，于是同时满足了另外两条流水线的入口条件：G16–G19「张开掌 → 保留 N 指」把它数成**四指**（slot 4，打开第 4 个应用）；G13 截图与 G05–G10 并掌挥把它当成**张开掌/四指并拢**，进入「等握拳」「等挥动」阶段并独占每一帧，导致 OK 的 0.6 秒保持永远到不了，动作完全不执行。
- **修复**（`GestureEngine.kt`）：新增 `okClaimsHand = features.ok && okPose`。只要 OK 手势开关打开且 OK 形态成立——
  - G16–G19 的张开掌入口与四个「保留 N 指」槽位均不成立，已锁定槽位或处于等待释放状态时立即回 `IDLE`，不等宽限期；
  - G13 的张开掌 arm（`WAIT_FIST`）直接清除；
  - G05–G10 的 `directionOpen`（四指并拢）入口同样让给 OK。
- 未改动 G26 拖动的放手判定：那里仍使用原始张开掌判据，OK 依旧代表放开。
- 新增回放用例：`okAfterAnOpenPalmFiresOkAndNeverOpensAnApp`、`okRescuesTheHandFromASlotThatLockedOnTheWayIn`（修复前两者均失败，可作为回归证据）。全部 119 用例通过，Debug APK 已装机。
- **待真机验收**：OK 是否已执行收藏、抬手/挥手后立刻做 OK 是否仍被延迟、OK 之后能否马上接 G05–G10 挥动与 G13 截图。

## 2026-10-04：G25 保持时长由 1 秒改为 0.6 秒

- G25「单指枪·竖向」的保持时间由 **1 秒** 改为 **0.6 秒**，与其他短保持手势（OK、C、Love、莲花指等）一致。产品负责人理由：默认动作为向上滑动（刷短视频翻页），等满一秒太慢。
- 改后 G25 落在倒计时门槛（保持 ≥ 1 秒才显示进度）以下，**不再显示「还需 N 秒」倒计时浮层**；这是与其他 0.6 秒手势一致的表现，不是缺陷。
- 变更位置：`GestureEngine.kt` 中 G25 的 `advanceStaticHold` 调用（`holdMs = 1000L` 与 `label` 一并去掉，走默认 600ms），`MainActivity.kt` 与 `CalibrationActivity.kt` 的 G25 姿势说明文案。
- 新增回放用例 `verticalGunHoldFiresAfter600msAndRequiresRelease`（0.55 秒不触发、0.65 秒触发一次、持续保持不重复、释放后可再次触发）。此前 G25 的保持节奏没有回放覆盖。
- 待真机验收：0.6 秒是否够快又不会因抬手经过此姿势而误翻页（过渡闸门已在该姿势生效，应能拦掉大多数过路形态）。

## 2026-10-04：G25 与 G35 默认绑定动作互换

- G25「单指枪·竖向」的默认动作由**下拉通知栏**改为**向上滑动**；G35「双指枪·竖向」的默认动作由**向上滑动**改为**下拉通知栏**。
- 动机：向上滑动（刷短视频翻页）属高频场景，单指枪比双指枪更容易快速打出；下拉通知栏属中低频系统功能，交给必须静止保持 1 秒的双指枪，误摆时来得及在中途收手。
- 只改 `GestureArchitecture.kt` 的 `defaultMappings` 与 `GestureArchitectureTest` 中对应的两条默认值断言（连同用例名）；编号、对外名称、识别算法、保持时长、所属签到解锁包均不变。
- 二者仍是普通绑定而非死绑，用户可在「手势练习与校准 → 手势动作映射」换绑任意动作；老用户本机已有的换绑结果不受影响（默认值只在没有用户偏好时生效）。
- 已同步文档：`GESTURE_ACTION_MAPPING_CHECKLIST.md`（映射总表）、`GESTURE_UNLOCK_PRODUCT_REQUIREMENTS.md`（初始权重表、第 11 天解锁包、第 12 天解锁说明）、`IDE_DEVELOPMENT_HANDOFF.md`（G35 小节与手势矩阵现状）、`GESTURE_REALTIME_ACCEPTANCE.md`（旧验收证据已注明为互换前的默认动作）。
- 待真机验收：互换后 G25 能否顺利翻页、G35 保持 1 秒能否拉下通知栏，以及与 G24（同属"枪"形、角度互不相同）是否互相影响。

## 2026-10-04：过渡姿势不得触发手势（验收问题 6）

- 抬手准备、换姿势、放手的途中，手经过别人的姿势形状时不得触发那个手势；只有停下来稳定住的姿势才算用户有意摆出的姿势。此前观测到 G19、G18、G22、G12、G07、G27 等约十次这类误触发。
- 判据基于"手是否还在变形"：按帧跟踪拇指尖与四个指尖相对手腕、以掌宽归一化后的位置，形变速度超过阈值即视为正在摆姿势；开始计时前必须先静止，计时途中再次变形就把计时归零重来。
- 只对静态保持类手势（G12、G14/G15、G20–G23、G24/G25、G27/G28、G34/G35）和 G16–G19 的槽位保持生效；挥动、滚动、拖动、音量、张掌序列等本就依赖手部运动的手势不受影响，整体平移也不算变形。
- 认可的成本：换姿势之后手势触发时间最多晚几十毫秒。
- 阈值（3.0 掌宽/秒、静置 60ms）为离线取值，**必须由真机数据复核**：既要看老样本的误触发是否消失，也要看正常手势有没有变迟钝。

## 2026-10-04：保持类手势执行后不得重复触发

- 播放/静音手势执行后保持不动，冷却结束不得再次执行；一次动作等于“姿势出现 → 保持 → 消失”这一个完整周期，只执行一次。
- 触发成功的锁存必须跨冷却期保留，冷却结束、手仍举着时保持静默；只有尚未触发的保持进度才能在重置时丢弃。
- 冷却期相机帧不进入识别引擎，恢复后的第一帧要能判定手部在冷却期间是否已经放下：姿势仍成立视为没放手，姿势已消失视为已放手并立即解锁。
- 控制手选择不得在暂停与恢复时被清空，避免恢复首帧被误判成丢手而让手势重新计时。
- 放手判定改为手连续消失约 600ms 才算松开，识别掉一两帧不得让手势重新计时；松开后的释放宽限统一为 800ms，覆盖 G22 握拳与 G23 小指。
- 本次只修 G22 与 G23 两个手势；其余保持类手势是否允许反复执行由产品负责人逐一点名后再改，不得自行推广。

## 2026-10-03：模型异步初始化必须随服务生命周期释放

- 同一前台服务实例同时只能执行一个 MediaPipe 手部模型初始化任务，重复启动命令不得并行创建多个 `HandLandmarker`。
- 模型初始化完成时必须确认服务仍存活且初始化代次有效；服务已经停止或任务已经过期时，不得把模型写回 Service，必须立即关闭未发布的 `HandPipeline`。
- 服务销毁必须使进行中的初始化任务失效，并关闭已经发布的识别管线；过期任务不得再弹出初始化失败提示。
- 构建通过不能代替真机内存验收；发布前需覆盖启动后立即停止、快速连续启停和模型加载中退出，并观察原生内存是否回落。

## 2026-10-02：多人、多手画面中的控制权规则

### 背景

用户距离摄像头较远或画面中出现其他人时，可能同时检测到多只手。旧实现只让 MediaPipe 返回一只手并直接取第一项，无法保证被识别的是最靠近摄像头、实际想要操作的手，可能导致后方人员误触动作。

### 已确认规则

1. 不增加授权动作，不要求用户先用食指或其他姿势取得控制权。
2. 画面中存在多只手时不因多手本身停止识别。
3. 视觉上最靠近摄像头的手独占控制权；即使该手没有做有效手势，后方其他手的任何手势也不得触发动作。
4. 使用掌部骨架的相对尺寸估算前后关系，不使用容易随姿势变化的指尖外接范围：主要参考手腕 0 和掌指关节 5、9、13、17。
5. 当前控制手持续锁定；另一只手的掌部尺度至少领先约 20%，并持续约 250ms，才允许接管，避免两手大小接近时逐帧跳变。
6. 当前控制手短暂遮挡时保留控制权；连续丢失约 300ms 后，才由当前画面中视觉上最近的手接管。
7. 控制权切换时必须清空上一只手的全部识别状态，包括静态保持进度、G22/G23 倒计时、轨迹、双击、组合动作、持续音量状态和光标平滑状态；新控制手从零开始识别。
8. 第一阶段最多检测两只手。发布前根据目标机型的识别帧率、耗电和发热结果，再决定是否扩大到三只手。
9. 单目摄像头没有真实深度，只能根据视觉尺度估算相对前后。该限制必须通过真机测试验证，不得宣传为精确距离或精确 80cm 判断。

### 初始实现参数

| 参数 | 初始值 |
|---|---:|
| MediaPipe 最大检测手数 | 2 |
| 初次控制手稳定时间 | 200ms |
| 挑战手掌部尺度领先比例 | 20% |
| 挑战手连续领先时间 | 250ms |
| 当前控制手连续丢失后接管 | 300ms |

### 验收要求

- 前方手保持自然状态时，后方手完成 G22、G23 或其他手势不得触发动作。
- 前方手正常完成手势时，后方手的姿势不得干扰识别结果。
- 后方手明显伸到前方并持续达到接管条件后，可以取得控制权。
- 两只手短暂交叉、遮挡或尺寸轻微波动时，不得频繁切换控制权。
- 接管发生时，上一只手已经积累的保持或轨迹进度不得由新手继续完成。
- 覆盖 40cm、60cm、80cm、100cm，两人同框、左右交叉、前后交换、不同大小手掌、左右手组合。
- 记录启用双手检测前后的识别帧率、CPU、耗电和发热；构建通过不能替代真机验收。
